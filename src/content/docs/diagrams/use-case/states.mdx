Each actor of the key rotation use case has one state machine.

## DID controller (Stuart)

Only one update is in flight. Do not make the next update before the last update has 6 confirmations. Two updates
with one `targetVersionId` make the DID fail with `LATE_PUBLISHING`.

<MermaidFile file="use-case/states-did-controller.mmd" />

## Aggregation Participant (Stuart)

Stuart checks its own entry before it signs. With a `k-of-n` fallback, a Beacon Signal can go out without the
signature of Stuart. If that signal has a wrong entry for the DID of Stuart, the DID is invalid.

<MermaidFile file="use-case/states-aggregation-participant.mmd" />

## Aggregation Service

The Aggregation Service sees hashes only. It needs a response from every participant. It broadcasts the Beacon Signal
with all `n` signatures, or with `k` signatures if the cohort has a `k-of-n` fallback.

<MermaidFile file="use-case/states-aggregation-service.mmd" />

## Relying party (Satoshi)

Satoshi trusts a new key only if the resolved DID document has it in `authentication`, and `versionId` is `N` or
more. [Resolve](/diagrams/resolve/) shows the resolution errors.
